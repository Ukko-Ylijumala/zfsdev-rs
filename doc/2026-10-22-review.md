## nvlist codec

### N1. XDR lists containing an empty number array fail to decode

**Where:** `decode_xdr_list` (`src/nvlist.rs:733-771`) and `array_count`
(`:787-797`).

**What:** for a scalar array with `nelem == 0`, the kernel's XDR encoder
writes no element count. `nvs_xdr_nvp_op` returns before the value
(`doc/reference/nvpair.c:3337-3339`). The pair's `encode_size`, however, is
computed by `nvs_xdr_nvp_size`, which counts the count word regardless
(`nvpair.c:3524-3536`: `4 + 4 * nelem`, `4 + 8 * nelem`). So the declared
pair size is 4 bytes larger than what was written — and for any enclosing
`DATA_TYPE_NVLIST` or `DATA_TYPE_NVLIST_ARRAY` pair (`nvpair.c:3550-3568`),
its `encode_size` is the sum of its children's `nvlist_size_xdr`, accumulating
+4 bytes per empty number array inside it.

The crate gets this wrong in three places:

1. `array_count` always reads a count word. With `nelem == 0` it reads the
   first word of the next pair (its `encode_size`) and fails with
   `ArrayCountMismatch { count: <next pair's size>, nelem: 0 }`. If the empty
   array is the last pair, it reads the terminator and fails with
   `Truncated`, or it misreads the parent's next word if the list is nested.
2. Even with the count skipped, `cur.pos = pair_end` (`:768`) jumps to
   `pair_start + encode_size`, 4 bytes past the real end. That desyncs every
   following pair. Inside a nested list, the parent's framing breaks too.
   The kernel's decoder never jumps by `encode_size`; it continues from
   where the value decode stopped.
3. The pre-decode check `(encode_sz as usize) > cur.remaining() + 8` (`:747`)
   only tolerates up to 2 empty number arrays (+8 bytes). A nested list (or
   trailing pair) containing ≥ 3 empty number arrays has `encode_sz` inflated
   by ≥ 12 bytes and is rejected with `BadPairSize` before decoding starts.

**Reproduced:** a hand-built XDR stream with an empty `uint64` array
followed by a `uint64` pair fails with `ArrayCountMismatch { count: 32,
nelem: 0 }`. With the empty array last, it fails with `Truncated`. The
native encoding of empty arrays is correct; only XDR is affected.

**Impact:** XDR is what on-disk vdev labels and `zpool.cache` use. How often
real labels carry an empty number array was not measured. The fuzz target
cannot find this, because the crate has no XDR encoder to produce the
kernel's quirk.

**Fix:** in `array_count`, return 0 without reading when `nelem == 0`. Drop
both `cur.pos = pair_end` after known types and the pre-decode
`(encode_sz as usize) > cur.remaining() + 8` check (the kernel's
`nvs_xdr_nvpair` at `nvpair.c:3630-3649` only checks `encode_len > 0 &&
decode_len > 0` and relies on stream reads for bounds). Keep `pair_start +
encode_sz` only for the unknown-type skip arm (`_ =>`), requiring `end <=
cur.buf.len()`. Pin it with a unit test that uses a byte-exact kernel stream
including ≥ 3 empty number arrays inside a nested list.

Byte arrays (`xdr_opaque`, no count word) and string arrays (one
`xdr_string` per element, no count word) do not have this problem.

### N2. `NvList::default()` lists are invisible to kernel lookups

**Where:** `#[derive(Default)]` on `NvList` (`src/nvlist.rs:124`), which gives
`nvflag == 0`. The doc on `NvList::new()` (`:305-308`) says this zero is
meant for decode output. `pack()` writes `self.nvflag` verbatim (`:373`), and
embedded lists carry theirs too (`:665-686`).

**What:** the kernel takes a root list's flag from the stream, and an
embedded list's from the stream's struct copy. On a list without
`NV_UNIQUE_NAME`/`NV_UNIQUE_NAME_TYPE`, every `nvlist_lookup_*` returns
ENOTSUP (`nvpair.c:1647-1648`).

**Failure scenario:** a caller builds props with the idiomatic
`NvList::default()` and passes them to `create`, `snapshot`, `set_prop` or
`pool_set_props`. All four accept a caller-built `&NvList`.
- `create` of a zvol fails with EINVAL even though `volsize` is present,
  because the lookup at `zfs_ioctl.c:3417-3419` fails.
- Create-time settings read by lookup (the encryption parameters,
  normalization/utf8only/casesensitivity) are silently not seen.

The crate's own roots all use `new()`, so nothing inside the crate hits
this.

**Fix:** implement `Default` as `new()`. Decoded lists set `nvflag` from the
stream either way, so decoding is unaffected.

### N3. Native and XDR decoders accept interior NUL bytes in pair names and XDR strings

**Where:** `decode_pairs` (`src/nvlist.rs:404-411`) and `read_xdr_string`
(`:215-221`).

**What:**
1. In native `decode_pairs`, `name_bytes = &blob[16..16 + name_sz - 1]` only
   checks that `blob[16 + name_sz - 1] == 0`, not whether `name_bytes`
   contains an interior NUL byte. The kernel's `i_validate_nvpair_name`
   (`nvpair.c:761`) enforces `strlen(NVP_NAME(nvp)) == nvp->nvp_name_sz - 1`.
2. In XDR `read_xdr_string`, `std::str::from_utf8(bytes)` accepts `\0`
   because NUL is valid UTF-8, allowing interior NULs in both XDR pair names
   and XDR `Str` / `StrArray` values.
3. Unpacking such a stream succeeds, but calling `pack()` on the resulting
   `NvList` fails with `NvError::EmbeddedNul`, breaking the `unpack` → `pack`
   round-trip invariant (masked in `fuzz/fuzz_targets/nvlist.rs:72` by
   `if let Ok(repacked) = list.pack()`).

**Fix:** reject `name_bytes.contains(&0)` in `decode_pairs` with
`NvError::BadName` and `bytes.contains(&0)` in `read_xdr_string` with
`NvError::EmbeddedNul`.

### N4. `NvList::push` / `add_*` does not deduplicate keys when `NV_UNIQUE_NAME` is set

**Where:** `NvList::push` (`src/nvlist.rs:314-317`).

**What:** in OpenZFS (`nvlist_add_common`, `nvpair.c:1261-1263`), adding a
pair to an `NV_UNIQUE_NAME` list removes any existing pair with the same
name. `NvList::push` always appends to `self.pairs`. While `NvList::get`
uses `.rfind()`, kernel ioctl handlers that walk input nvlists with
`nvlist_next_nvpair` iterate the linked list `priv->nvp_list`, which keeps
every pair decoded from the stream (`nvs_decode_pairs`, `nvpair.c:2465`).

Passing duplicate snapshot names to `ZfsHandle::snapshot` (e.g.
`&["tank/ds@s", "tank/ds@s"]`) packs two pairs with the same name into
`snaps`, and `zfs_ioc_snapshot` (`zfs_ioctl.c:3620-3625`) rejects two
snapshots of the same filesystem with `EXDEV`.

**Fix:** in `NvList::push`, when `self.nvflag & NV_UNIQUE_NAME != 0`, retain
only pairs with `p.name != name` before pushing (matching C
`nvlist_add_common`), while keeping raw append on decode.

### N5. `NvList::pack()` has unbounded recursion

**Where:** `encode_pairs` / `encode_value` (`src/nvlist.rs:583-702`).

**What:** `NvList::unpack` enforces `depth <= MAX_DEPTH`, returning
`NvError::TooDeep`, but `NvList::pack` has no depth check at all: packing a
deeply nested `NvList` overflows the thread stack.

**Fix:** pass `depth` through `encode_pairs` and return `Err(NvError::TooDeep)`
when `depth > MAX_DEPTH`.

## ioctl usage

### I1. Any ENOMEM is retried, and mutating ioctls are re-issued

**Where:** `ioctl_nv_in` (`src/ioctl.rs:1393-1399`) and `write_ioctl`
(`:2009-2012`).

**What:** the kernel signals "output buffer too small" from `put_nvlist`
(`zfs_ioctl.c:1288-1296`):
```c
if (size > zc->zc_nvlist_dst_size) {
    error = SET_ERROR(ENOMEM);
} else {
    error = xcopyout(packed, (void *)(uintptr_t)zc->zc_nvlist_dst, size);
    if (error == 0)
        zc->zc_nvlist_dst_filled = B_TRUE;
}
zc->zc_nvlist_dst_size = size;
```
Note two critical details:
1. When `put_nvlist` fails with `ENOMEM`, **`zc_nvlist_dst_filled` remains
   `B_FALSE` (`0`)**! The signal that `put_nvlist` needed a larger buffer is
   `(zc.zc_nvlist_dst_size as usize) > dst.len()`, *not*
   `zc_nvlist_dst_filled != 0`.
2. In `zfsdev_ioctl_common` (`zfs_ioctl.c:7799-7843`) and legacy write
   handlers, `vec->zvec_func` **executes the mutation before `put_nvlist`
   runs**. Retrying `write_ioctl` on `ENOMEM` under *any* condition re-runs
   the non-idempotent mutation (e.g. `RECV_NEW` reading from a partially
   consumed stream fd, `SEND_NEW` writing a second stream into the fd, or
   `CREATE`/`SNAPSHOT` running twice).

Furthermore, on a handler-originated `ENOMEM` (where `zc_nvlist_dst_size` was
not grown past `dst.len()`), `ioctl_nv_in` and `events_next` loop forever
doubling `dst` until OOM.

**Fix:**
- In `write_ioctl`: **never retry on `ENOMEM`**. Size `dst` upfront to
  `DST_INITIAL.max(src_len.saturating_mul(2)).min(DST_MAX)` (matching
  `lzc_ioctl`'s `MAX(size * 2, 128 * 1024)`) and issue the ioctl once.
- In `ioctl_nv_in` and `events_next`: retry on `ENOMEM` only when
  `(zc.zc_nvlist_dst_size as usize) > dst.len()` and `<= DST_MAX` (128 MiB).
- In `error_log`: cap `ENOMEM` buffer doubling at `DST_MAX`.

### I2. Write errors list counters and shapes that aren't errnos

**Where:** `collect_element_errors` (`src/ioctl.rs:391-405`). It treats
every `Int32`, `Int64` and `Uint64` value in a failed write's outnvl as an
errno, and recurses into nested lists.

**What goes wrong:**
- **RECV_NEW:** the handler always adds the counters `read_bytes` and
  `error_flags` (u64), and the `errors` list (`zfs_ioctl.c:5483-5485`). A
  failed receive reports elements such as "read_bytes: Unknown error 312"
  and "error_flags: Success".
- **VDEV_SET_PROPS:** a failed set reports `{<prop>: {source: 0, value:
  <errno>}}` (`vdev_prop_set` in 2.2.2 `vdev.c`). The flattening produces
  "source: Success; value: …" and loses the property's name.
- **Smushed outnvls:** when the per-element errors don't fit, the kernel
  drops entries and adds an int32 `N_MORE_ERRORS` holding the drop count
  (`nvlist_smush`, `zfs_ioctl.c:1304-1335`). The crate renders that count
  as an errno.

**Fix:** skip `"read_bytes"`, `"error_flags"`, and `"N_MORE_ERRORS"`, skip
`errno == 0`, and recognise the `{value, source}` sub-list shape from
`VDEV_SET_PROPS` (reporting `value` as the errno under the parent property's
name).

### I3. `pool_stats` drops the pool's real errno

**Where:** `pool_stats` (`src/ioctl.rs:1416-1420`).

**What:** when `spa_get_stats` fails but still produces a config, as for a
faulted or unavailable pool, the handler returns *success*. The real errno
is in `zc_cookie` (`zfs_ioctl.c:1615-1624`). libzfs reads it and marks the
pool `POOL_STATE_UNAVAIL`. The crate returns the config as if the pool were
fine.

**Fix:** check `zc.zc_cookie` or surface it when non-zero.

### I4. `objset_recvd_props` fails where it should return an empty list

**Where:** `objset_recvd_props` (`src/ioctl.rs:1504-1515`).

**What:** the handler returns ENOTSUP for any dataset that has never
received properties (`zfs_ioctl.c:2159-2160`). That is most datasets.

**Confirmed live** on `rpool`, `storage` and `data/test/rand`: each fails
with EOPNOTSUPP. The method's doc says "empty if nothing was received",
and the live test's comment says the error only happens on old pools. Both
are wrong.

**Fix:** map ENOTSUP (`EOPNOTSUPP`) to an empty `NvList::new()`, and correct
the test comment.

### I5. `ZFS_ERR_*` errnos print as "Unknown error"

**Where:** error display (`ZfsError::Ioctl`, `ZfsError::Write`, element
errors), and the doc of `vdev_get_props` (`src/ioctl.rs:1527-1530`).

**What:** `zfs_errno_t` (`zfs.h:1547` on) starts at 1024: CHECKPOINT_*,
DISCARDING_CHECKPOINT, NO_CHECKPOINT, DEVRM_IN_PROGRESS, VDEV_TOO_BIG,
IOC_CMD_UNAVAIL, IOC_ARG_UNAVAIL, IOC_ARG_REQUIRED, IOC_ARG_BADTYPE,
WRONG_PARENT, FROM_IVSET_GUID_*, BADPROP, VDEV_NOTSUP, the
RESUME_EXISTS/STREAM_* receive errors and others (up to 1052 in 2.4).
`strerror` knows none of them, so they show as "Unknown error 1029".

The `vdev_get_props` doc says older kernels reject the ioctl with EINVAL.
In fact the ordinal is beyond the table there, so 0.8–2.1 return
`ZFS_ERR_IOC_CMD_UNAVAIL` (1029; `zfs_ioctl.c:7671`, `:7680`).

**Fix:** mirror `zfs_errno_t` (`ZfsErrno`) in `enums.rs`, expose
`ZfsError::zfs_errno()`, and use `ZfsErrno` in `ElementError::Display` and
`errno_hint`. Correct the `vdev_get_props` doc.

### I6. `error_log` returns duplicate entries

**Where:** `error_log` (`src/ioctl.rs:1677`).

**What:** the kernel merges four sources: the scrub and last error logs
and the in-core scrub and last error lists. The same block can therefore
appear more than once. libzfs sorts and deduplicates (`zpool_get_errlog`).
zfs-browser does it itself (`../zfs-browser/src/node.rs:1389-1400`). The
doc presents the result as the list `zpool status -v` prints.

**Fix:** deduplicate entries in `error_log`.

### I7. `vdev_set_props` and `pool_set_props` allow inputs that panic the kernel

**Where:** `vdev_set_props` (`src/ioctl.rs:2312-2321`) and `pool_set_props`
(`:2052-2056`).

**What:** both methods accept arbitrary `(prop, value)` pairs (`&NvData` /
`&NvList`) and pass them straight to `ZFS_IOC_VDEV_SET_PROPS` /
`ZFS_IOC_POOL_SET_PROPS`. In OpenZFS (`vdev_prop_set` /
`vdev_props_set_sync` in `module/zfs/vdev.c:6303-6680`, and
`spa_prop_validate` / `spa_sync_props` in `module/zfs/spa.c:730-952,
10754-10937`), the kernel assumes `libzfs` has already filtered out read-only
properties and validated `nvpair_type`:
- In `vdev_props_set_sync`, passing a non-`Str` `NvData` for `"comment"` or a
  user prop (`"ns:name"`), or a string ≥ `ZAP_MAXVALUELEN` (8192), or an
  out-of-range `Uint64` for `"failfast"` / `"scheduler"`, triggers a kernel
  `VERIFY` / `panic` in TXG sync context.
- In `spa_prop_validate` / `spa_sync_props`, passing a non-`Str` `NvData` for
  a pool user prop or `"compatibility"`, or passing read-only pool props
  (`"health"`, `"size"`, …), triggers `VERIFY` panics or writes
  bogus entries into `spa_pool_props_object` in the MOS.

**Correction after implementation audit:** the pool `ashift` property is
settable (0 or 9–16); the vdev `ashift` property is read-only. On the verified
2.2–2.4 releases, `failfast` accepts only 0/1, and the vdev booleans
`allocating`, `sit_out`, `autosit`, and `slow_io_events` also need bounds.

**Fix:** keep the existing `vdev_set_props` and `pool_set_props` signatures
for API compatibility, and validate property names, editability, `NvData`
types, boolean/index ranges, and `< 8192` string lengths client-side
(returning `ZfsError::Invalid` before any ioctl is issued).

### I8. `hold` and `release` silently return `Ok` when target/tag is `ENOENT`

**Where:** `hold` (`src/ioctl.rs:2227-2235`) and `release` (`:2242-2250`).

**What:** in `dsl_dataset_user_hold_check` (`dsl_userhold.c:135-141`) and
`dsl_dataset_user_release_check` (`dsl_userhold.c:394-403, 478-492`), when the
pool exists but the target snapshot (or hold tag) does not exist, the kernel
records `snap -> ENOENT` (or `snap#tag -> ENOENT`) in `outnvl` and **returns
`0` from the ioctl**. Because `write_ioctl` only inspects `outnvl` for
`ElementError`s when `self.ioctl` returns `Err`, `hold` and `release` return
`Ok(outnvl)` on a missing snapshot or tag.

**Fix:** keep `Result<NvList>` for API compatibility, and in `write_ioctl`
(for `WriteOp::Hold | WriteOp::Release`), if `outnvl` contains per-element
errors on `Ok`, return `Err(ZfsError::Write { op, err, elements })`.

### I9. `list_next` swallows `ENOENT`, returning `Ok(vec![])` on a missing pool

**Where:** `list_next` (`src/ioctl.rs:1965-1969`).

**What:** `zfs_ioc_dataset_list_next` (`zfs_ioctl.c:2255-2256`) and
`zfs_ioc_snapshot_list_next` (`:2324-2325`) always translate end-of-iteration
`ENOENT` into `ESRCH`. An `ENOENT` returned by the ioctl therefore comes from
`pool_status_check` when the pool itself does not exist. Catching `ENOENT`
alongside `ESRCH` makes `datasets("no_such_pool")` and
`snapshots("no_such_pool")` return `Ok(vec![])` instead of `Err(ENOENT)`.

**Fix:** only treat `libc::ESRCH` as end-of-iteration (`Ok(out)`), and
propagate `libc::ENOENT` as `Err`.

### I10. `recv_new` returns `ZfsError::Invalid` instead of kernel `Write` error on root target

**Where:** `recv_new` (`src/ioctl.rs:1877-1883`).

**What:** when `fsname` has no `'/'` (e.g. `"tank@snap"`) and
`self.objset_stats("tank")` fails, `recv_new` returns
`ZfsError::Invalid("receive: pool 'tank' does not exist")` instead of passing
`fsname` as `zc_name` to `ZFS_IOC_RECV_NEW` so the kernel returns its
structured `ZfsError::Write` (`ENOENT`).

**Fix:** `let target = if self.objset_stats(fsname).is_ok() { fsname } else {
fsname.rsplit_once('/').map_or(fsname, |(parent, _)| parent) };`.

## Other modules

### S1. `xattr=on` stores the wrong mode on 2.3 and later

**Where:** `src/props.rs:238-245` (parse) and `:759` (display).

**What:** `parse_prop_value("xattr", "on")` returns 1 (`ZFS_XATTR_DIR`).
Since zfs-2.3.0 (commit e419a63bf, "xattr dataset prop: change defaults to
sa"), `xattr_table` maps "on" to `ZFS_XATTR_SA` (2); through 2.2.x it mapped
to DIR. Both values are valid, so on a 2.3/2.4 kernel the crate quietly
stores directory-based xattrs where `zfs set xattr=on` stores SA. Verified
in `zfs_prop.c` at both tags.

**Display:** "on (dir)" matches no release. Up to 2.2, `zfs get` prints
"on" for 1. 2.3 prints "dir" for 1 and "on" for 2. 2.4 prints "dir" for 1
and "sa" for 2.

**Fix:** parse "on" to SA when the running kernel is 2.3 or newer (this is
a write argument, so a version check is legitimate here), or refuse "on"
and require `dir`/`sa`. Display by value: "dir", "sa", "off".

### S2. Rebuild progress and ETA use bytes issued, not scanned

**Where:** `RebuildStats::progress`, `pass_rate` and `eta`
(`src/stats.rs:534-537`, `:586-599`).

**What:** every release from 2.0.7 to 2.4.4 computes the rebuild's % done in
`print_rebuild_status_impl` as `bytes_scanned / (bytes_est + 1)`, and its
ETA as `(est − scanned) / scan_rate`. The module says the crate computes
these "the way zpool status does". Since 2.2, `vdev_rebuild_range` counts
ranges outside the DTL as scanned and skipped but never issued. So issued
bytes can never reach the estimate, and a finished rebuild stays below 1.0.
Verified in `zpool_main.c`.

**Probe:** scanned 90G of 100G, issued 10G, skipped 80G. The crate says
0.100 and an ETA of 900 s; `zpool` says 90% and about 11 s.

### S3. The `flush` counter slot is actually TRIM

**Where:** `ZioCounters` (`src/stats.rs:162-176`).

**What:** `vdev_stat_update` (0.8.6 through 2.4.4) reports TRIM in the
ZIO_TYPE_IOCTL slot (`FLUSH` from 2.3), with the comment that this keeps the
`vdev_stat_t` layout. Flush zios run at `ZIO_PRIORITY_NOW` and are never
counted. Verified in 2.2.2 `vdev.c:4864-4869`. The crate's doc says TRIM has
no slot and names the field `flush`. The kernel's own `trim_ops` vdev
property reads this same slot.

**Fix:** rename to `trim` (or document it under `flush`, with a deprecation
path), and correct the doc.

### S4. Fragmentation is `Some(0)` below the top level

**Where:** `src/stats.rs:234-236`, `:282`.

**What:** `vs_fragmentation` is written only for a concrete top-level vdev
(`vd == vd->vdev_top && vdev_is_concrete(vd) && !aux`); every other vdev
carries 0. The crate reports `Some(0)` ("0% fragmented") for each disk,
where its doc promises `None`. `zpool list -v` hides the value by position,
not by value. Separately, on 2.2.2 the VDEV_GET_PROPS `fragmentation`
property reads a field nothing writes, so it is always 0, even at the top
level. That is a kernel bug the crate passes through.

**Fix:** decide by the vdev's position, which the tree walker knows: `None`
unless top-level.

### S5. `PropEntry::source` accepts non-ancestor or `"$"` strings as `Inherited`

**Where:** `PropEntry::source` (`src/props.rs:572-578`).

**What:** any non-empty string source `s` other than `owner` and `$recvd` is
returned as `PropSource::Inherited(Some(s))`. In `libzfs` (`get_source`), a
string starting with `'$'` (internal sentinel) maps to `ZPROP_SRC_NONE`
(`PropSource::None`), and an inherited source must be an ancestor prefix of
`owner` followed by `'/'` or `'@'` (for snapshots inheriting from their
parent dataset).

**Fix:** require `!s.starts_with('$') && owner.starts_with(s.as_str()) &&
matches!(owner.as_bytes().get(s.len()), Some(b'/' | b'@'))` for
`PropSource::Inherited`, returning `PropSource::None` otherwise.

### K1. One non-UTF-8 mount path breaks `dataset_of` everywhere

**Where:** `src/mount.rs:71`, `fs::read_to_string("/proc/self/mountinfo")`.

**What:** mountinfo escapes only space, tab, newline, backslash and `#`.
Any other byte, Latin-1 `é` for example, arrives raw. One such mount
anywhere on the host makes the whole read fail with `InvalidData`. After
that, `dataset_of` fails for every path.

**Reproduced** with `unshare -rm` and a tmpfs mounted at a Latin-1 path:
`dataset_of("/home")` returned `Err(InvalidData)`; outside the namespace it
returns `rpool/home`.

**Fix:** read bytes and split on bytes. `unescape` already yields bytes.

### K2. One non-UTF-8 byte makes the debug log unreadable

**Where:** `read_dbgmsg` (`src/kstat.rs:811-812`).

**What:** the same `read_to_string` failure. The debug log carries
user-controlled bytes: full command lines and property values
(`spa_history.c:293-310`) and vdev paths. One non-UTF-8 byte makes the log
unreadable until the entry ages out of the 4 MiB ring. Found by reading
the code; not demonstrated live (reading the log needs root).

**Fix:** read bytes, then `String::from_utf8_lossy`. See P1.

### K3. Prefetch hit ratio too high on 2.2.4 and later

**Where:** `dmu_prefetch_ratio` (`src/kstat.rs:266-269`).

**What:** zfetchstats gained `future`, `stride` and `past` in 2.2.4 (commit
5e5fd0a17). Each prefetch access now increments exactly one of hits,
stride, future, past or misses. Dividing by `hits + misses` leaves the new
classes out of the denominator. `arc_summary` divides by all five.

**Fix:** add the three fields to the denominator when present, the way
`iohits` is handled for the ARC.

### K4. `named_line` splits on `u8` tokens inside multi-word names, and `is_pool_name` is lax

**Where:** `named_line` (`src/kstat.rs:187-199`) and `is_pool_name`
(`:297-299`).

**What:**
1. `named_line` splits at the first token after the first word that parses as
   `u8` (`0..=255`). For an SPL-formatted line (`%-31s %-4d <value>`) whose
   multi-word name has a second token in `0..=255` (e.g. `"stage 4 count"`),
   it splits inside the name instead of at column 32.
2. `is_pool_name` only checks `starts_with(ascii_alphabetic) && !contains('/')`,
   accepting reserved names (`mirror`, `raidz`, `draid`) and invalid
   characters (`$`, spaces).

**Fix:** in `named_line`, check column 32 first when byte 31 is `' '` and
restrict kstat data types to `0..=8`; in `is_pool_name`, enforce allowed pool
characters (`[A-Za-z0-9_.:-]`), the kernel's length limit, and its exact
reserved names (`pool_namecheck`). The broader reserved-prefix restrictions
apply only during creation/import in libzfs: kstat readers must accept
legacy imported pools such as `mirrorpool`, `raidz1`, `spare`, and `log`.

## Performance

### P1. procfs reads: one large read instead of `read_to_string`

`fs::read_to_string` starts with a 32-byte probe and grows, about 10
`read()` calls per file (seen under strace). Each read that needs fresh
records re-enters `kstat_seq_start`, which re-runs the kstat's update
callback. For arcstats that sums the per-CPU counters every time. Measured
on the review host against a 64 KiB pre-sized `read_to_end`:

| File                    | `read_to_string` | Pre-sized buffer  |
|-------------------------|------------------|-------------------|
| arcstats                | 1.34 ms          | 0.53 ms (3 reads) |
| one objset kstat        | 96 µs            | 42 µs             |
| zfetchstats             | 38 µs            | 24 µs             |
| txgs                    | no change        | no change         |
| whole poll, ~90 objsets | ~8.6 ms          | ~3.8 ms           |

Parsing is not the cost (`Kstat::parse` of arcstats: 35 µs in release).
Fewer update passes also make the counters within one read more consistent.
A single `read_proc` helper (open, `read_to_end` into ~64 KiB, then
`from_utf8_lossy`) would also fix K1 and K2, and narrow the EIO window in
`read_objset_kstats`.

### P2. Lazy error construction in the nvlist decoder

`decode_value`'s `need` closure (`src/nvlist.rs:437-443`) uses
`ok_or(NvError::ValueOverflow { name: name.to_string(), .. })`. That
allocates a copy of the pair name on every value decoded, including
successful ones. `ok_or_else` brought unpacking this host's 60 KB `storage`
pool config from about 55 µs to 47 µs (about 15%). The ioctl itself takes
about 1.4 ms, so the absolute gain is small. `scalar_array` (`:444-447`)
also collects a `Vec<&[u8]>` per array that the callers could iterate
directly.

### P3. Single-pass `NvList::pack()` without per-pair heap allocations

`encode_pair` (`src/nvlist.rs:598-703`) calls `encode_value`, which allocates
a temporary `Vec<u8>` on the heap for **every single pair** (even a scalar
`Uint64` calls `.to_le_bytes().to_vec()`) and recursively allocates and copies
intermediate `Vec<u8>` buffers for every nested `NvList` and `ListArray`.
Writing headers and values directly into `out: &mut Vec<u8>` and patching
`nvp_size` at `pair_start` reduces `NvList::pack()` from
$O(\text{pairs} + \text{sublists})$ allocations to a single `Vec<u8>`
allocation.

### P4. Smaller allocation and syscall wins

- **`pool_history` record length inspection (`ioctl.rs:1460-1473`):** when
  `consumed == 0` and `bytes_read >= 8`, the next record's 8-byte `reclen` is
  already in `buf[..8]`. Inspecting `reclen` avoids 6 blind buffer-doubling
  ioctls (up to 16 MiB) when `reclen` is corrupt (`0` or `> 16 MiB`), and
  resizes `buf` in a single step when `reclen` is a valid large record.
- **`mount::find_mount` (`mount.rs:112-139`):** deferring `unescape_path` on
  `mount_point` until *after* filtering by `m.dev == dev && m.fstype == "zfs"`
  avoids allocating a `Vec<u8>` and `PathBuf` for every non-matching line in
  `/proc/self/mountinfo`.
- **Static string lookups (`props.rs:197`, `kstat.rs:254-262`,
  `stats.rs:812`):** deriving `IntoStaticStr` on `VdevProp` avoids allocating
  39 `String`s per `vdev_get_props` call; static counter names on `ArcClass`
  avoid 4 `format!` allocations per `hit_ratio` call; iterating
  `nv.pairs.iter().rev()` directly in `VdevStatsEx::decode` avoids an
  intermediate `Vec<&NvPair>`.
- **Unchanged pool configs:** `pool_configs` always passes cookie 0.
  POOL_CONFIGS returns EEXIST when given the current config generation. A
  poller could pass back the last generation and skip decoding when nothing
  changed.
- **`recv_new`'s existence check:** it uses `objset_stats`, which fetches
  every property. A no-dst existence probe like `lzc_exists` would do.
- **`userspace_many`:** the buffer is 64 entries (about 17 KiB). A larger
  buffer means fewer ioctls on datasets with many users. A non-full batch
  means the end was reached, which would save the final empty call.
- **`snapshot_stats` on pre-2.2 kernels:** the simple-mode walk runs to
  completion before the fallback to the full listing. The first entry is
  enough to tell.

## Follow-up implementation audit, 2026-10-23

The first implementation pass (`e97c275` through `cab5cb7`) left gaps despite
the completed chunk checkboxes. The follow-up fixes cover the nine audit
findings and strengthen the scoped plan's regression coverage:

- Enforce pool/vdev numeric bounds and string/name limits before issuing
  an ioctl, including `failfast=2` and the other TXG-panic-prone indices.
  Pool editability uses a pool-specific allowlist; import-only properties
  are rejected. `dedup_table_quota` is accepted as a uint64.
- Propagate `pool_stats`'s cookie errno, render ZFS-specific read and write
  errors, and correct the received-properties test and vdev ioctl docs.
  Bound the remembered output-buffer headroom by `DST_MAX` too.
- Keep `xattr=on` version-dependent on Linux and reject the ambiguous alias
  when the kernel version is unavailable. Explicit `dir`/`sa` remain
  portable. The FreeBSD library build is checked.
- Decode mountinfo directly from bytes, preserving non-UTF-8 mount points
  and bind roots. Tests use raw invalid UTF-8, not just ASCII octal escapes.
- Use wide counter sums for ratios and saturate the `accesses()` result.
  The kstat fuzz target now exercises the ratio bounds as well.
- Apply existing-pool name rules when reading kstats and preserve the
  debug message's indentation while validating timestamp columns.
- Make nvlist decode errors lazy and iterate scalar-array chunks directly
  (P2). Reject unsupported root/embedded versions, and exercise the empty
  numeric-array XDR size inflation in both lists and list arrays with and
  without a following root pair.
- Clarify that raw stat decoders lack tree position. `VdevEntry::stats()`
  supplies the fragmentation availability check, including auxiliary and
  non-concrete devices, while retaining genuine top-level 0% values.

The original "Minor findings" and optional performance suggestions remain
a backlog except for the items explicitly included in the scoped plan or
listed above; the chunk checkboxes describe that scoped implementation.
